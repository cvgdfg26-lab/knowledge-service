# 项目面试与评估计划

本文件服务于大模型应用开发 / RAG 工程师求职准备。正式系统需求见 [多业务线知识服务平台需求说明](./知识库项目需求梳理.md)，功能优先级和上线条件以该文档为准。

实施约定见 [开发手册](./开发手册.md)。CPU 服务器部署 FastAPI/Uvicorn 的 kb-import:8000、kb-query:8001、kb-worker，以及 MinIO、Milvus、etcd、Neo4j、MongoDB；GPU 服务器部署唯一 BGE-M3 1024 维稠密/稀疏嵌入与 BGE-Reranker-Large。LangGraph 编排导入与问答，HTML5/原生 JavaScript 提供页面；生成模型使用厂商 API，MinerU 也直接调用 API，两者均不自部署。

## 1. 项目呈现方式

按企业知识服务项目组织业务背景、角色、流程、接口、架构、验收和运行材料，展示对生产问题的处理能力。

讲解依次说明：业务场景 → 核心链路 → 关键难点 → 方案取舍 → 实验结果 → 工程验证 → 当前限制。教育作为深入讲解场景，其他领域用于说明复用能力和业务差异。

各项能力维护一张证据表：

| 状态 | 含义 | 对应材料 |
| --- | --- | --- |
| 已设计 | 已写出流程、接口与边界 | 需求、架构、决策说明 |
| 已实现 | 有可运行代码 | 代码入口和演示 |
| 已验证 | 在明确条件下通过测试或演练 | 测试记录、实验报告 |
| 已运行 | 在指定环境持续使用过 | 发布记录、监控与反馈 |

业务场景设定可以完整，结果和经历按证据表描述。容量规划、合成压测、预发布部署和真实用户运行分别标注，不混写为已上线业务。

## 3. 数据规模与评估集

### 3.1 资料建设

实际质量验证先准备约 60–100 份逻辑文档：教育 40–60 份，其余领域各 5–10 份。根据资料质量调整，不为数量填充低质量内容。

记录文档、字符/页、片段、格式、领域、来源、版本和处理失败数。公开材料与自编演示材料分别标注；一份文档切出的多个片段不能当成多份文件。

主需求中的 10,000 文档、200,000 片段是容量假设。容量验证若使用合成数据，报告说明生成方式和限制，质量成绩仍使用真实核对的资料。

### 3.2 题集要求

建议 150 道问题：教育 100 道、金融 20 道、其余领域各 10 道。开发集约 90 道、冻结测试集约 60 道，按问题族分组划分并保持主要类型覆盖。

样本字段：question_id、领域、问题类型、问题、答案要点、是否可回答、文档与版本、原文证据、预期处理行为、标注说明。

涵盖精确术语、单文档事实、跨文档综合、资料不足、版本冲突、领域隔离和提示注入。追问、权限、生命周期和故障能力另建相应回归用例，避免与知识问答准确率混成一个分数。

检索语料包含测试问题所需原始文档是正常设置，但测试题、答案和标注文件不能进入业务索引。自动生成题只作候选，必须人工核对。

## 4. 指标口径

检索和生成分别评估，可参考 [Amazon Bedrock 的 RAG 评估说明](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)。项目不要求采用该服务。

| 指标 | 口径 |
| --- | --- |
| Hit@5 | 可回答题中，前 5 个最终片段覆盖至少一个有效证据的题数 / 可回答题数 |
| 证据 Recall@5 | 被前 5 个片段覆盖的标注证据数 / 全部标注证据数；跨文档题另报完整证据覆盖率 |
| 答案正确率 | 满足答案要点且无实质错误的可回答题数 / 可回答题数 |
| 引用支持率 | 引用确实支持的可核验结论数 / 已提供引用的可核验结论数 |
| 引用覆盖率 | 附有有效支持引用的关键结论数 / 需要证据的关键结论数 |
| 资料不足处理正确率 | 正确说明依据不足且未编造的不可回答题数 / 不可回答题数 |
| 过度拒答率 | 不合理拒答的可回答题数 / 可回答题数 |
| 延迟 | 检索、重排、首字和总耗时；报告 P50/P95、样本量、超时与失败 |
| 成本 | 输入/输出 Token、索引和模型资源；按记录的用量和单价估算 |

改变切分方案时按文档和原文证据匹配命中，不能只比较不同方案的 chunk_id。报告分子/分母与各领域结果。小样本结果不外推为普遍效果。

人工判断使用固定评分规则；模型裁判记录模型、提示词和参数，并抽检与人工判断的差异。优化质量同时检查过度拒答与引用覆盖，避免通过少答来提高表面分数。

## 5. 四组必做对照实验

| 实验 | 对照 | 重点问题 |
| --- | --- | --- |
| E01 | Milvus BM25 与选定 Profile 的纯稠密检索 | 精确书名、课程名、产品代码与同义表达各有什么差异？ |
| E02 | 同一 Profile 稠密与稠密 + BGE-M3 稀疏 | 是否改善覆盖？哪些问题退步？RRF 怎样配置？ |
| E03 | 混合检索开启/关闭 GPU BGE-Reranker-Large | 排序和答案是否改善？排队、网络、推理总延迟与资源代价如何？ |
| E04 | 固定长度与结构切分 | 章节、列表、表格上下文是否更完整？片段大小如何影响噪声？ |

固定语料、题集、模型、提示词及其他配置，一次尽量只改变一个因素。开发集用于选参数，冻结测试集用于最终报告，不针对测试集反复优化。

嵌入固定为 BGE-M3，不再比较多个嵌入模型。P1 补充 E05 图谱扩展开关实验：固定文本召回、重排、切分、生成和题集，比较关系题的完整证据覆盖、正确率、越权/过期关系拦截及总耗时。图谱范围与快照记录在 manifest；未启用扩展时标为未执行。

部署实验覆盖 GPU 断网/OOM 时的 BM25 降级、Neo4j 故障时文本问答、MinerU 429/超时/未知提交与轮询恢复、导入/查询独立重启后会话及发布一致性。记录网络/排队/推理分项，不只报告模型内部耗时。

qwen3-vl-flash 图片分支属于 P1，启用后另建图表理解和来源核对用例，不能混入文本 RAG 成绩宣称图片检索能力。

记录代码版本、数据摘要、模型标识、采样参数、运行环境与运行时间。效果接近或有明显随机波动时合理重复并说明波动，不挑最好的一次作为唯一成绩。

至少保留 10 个失败案例：问题、标准证据、系统结果、失败阶段、原因、处理方式和复验结果。未修复案例也应保留，作为边界与后续计划。

## 6. 求职推进顺序

1. 做出教育检索问答闭环，能看原文并展示资料不足处理。
2. 完成混合检索、重排、结构切分与四组实验。
3. 实现权限、发布一致性、文档更新和异常处理，完成负向验证。
4. 接入其余领域，完成可复现部署、故障演练和运行材料。
5. 汇总实际完成范围，准备简历、演示和技术讲解，即可开始投递。

正式上线按主需求的试点条件执行。尚无真实机构试点时，以预发布环境验证作为当前交付状态；求职材料不等待所有 P1 扩展能力完成。

## 7. 五分钟演示

1. 30 秒说明业务流程、使用者和范围。
2. 1 分钟展示教育问答、来源与原文定位。
3. 1 分钟对比基础检索与优化方案，解释证据变化。
4. 1 分钟展示权限拒绝或更新发布，再展示资料不足。
5. 1 分钟展示实验成绩与一个失败案例，解释代价和限制。
6. 剩余时间切换其他领域，说明元数据与适用规则。

准备固定问题、可复现资料和约 5 分钟录像。截图、录像与离线结果注明版本，网络异常时明确使用备用材料。

## 8. 面试追问清单

- 为什么选择 RAG？长上下文、关键词检索和微调的适用条件是什么？
- 切分长度、重叠与章节结构如何影响结果？如何处理表格？
- 混合检索怎么融合？为什么不直接相加不同检索分数？
- BGE-M3 学习型稀疏与 BM25 有什么区别？Milvus 每条召回如何带相同授权过滤？
- BGE-M3 为什么固定 1024 维与同一快照？为什么相同维度也可能需要重建索引？GPU 故障时为什么稠密/稀疏都不可重新编码？
- LangGraph state、MongoDB 消息与 checkpoint 各保存什么？节点恢复如何避免重复发布或重复计费？
- MinerU API 如何上传私有文件、保存远程 ID、恢复轮询和安全下载产物？未返回任务 ID 的提交超时怎样处理？
- MinerU 页/块坐标如何映射到引用？MinIO 私有图片怎样预览、撤权和清理对象版本？
- kb-import:8000 和 kb-query:8001 各拥有哪些接口？共享登录/权限和 Schema 升级如何处理？两个 Compose 的网络怎样跨主机连接？
- MongoDB、Milvus、Neo4j、MinIO、etcd 各存什么？为什么图谱发布仍由 MongoDB 指针决定？
- Neo4j 关系如何绑定原文证据并逐跳过滤授权？为什么实体同名不能直接跨库合并？图谱比文本检索带来哪些实测收益？
- 重排候选数与上下文数如何选择？在哪些情况下重排反而退步？
- 如何判断证据不足？检索分数为什么不是正确概率？
- 如何评估引用是否支持结论？如何处理部分支持和版本冲突？
- 如何防止评估泄漏？模型裁判会有什么偏差？
- 发布和索引如何保持一致？任务重复投递如何保证幂等？
- 用户撤权后缓存、原文、历史回答和正在输出的会话如何处理？
- 模型不可用、重排失败、任务中断如何恢复？
- 恢复旧备份后如何避免已删除资料重新暴露？
- 性能与可用性分别怎样测量？外部模型限制如何计入？
- 本人实现了什么，依赖库完成了什么？当前哪些只是设计？
- 若扩大资料量与并发，哪个组件先成为瓶颈？扩展依据是什么？

回答应对应代码、实例或测试记录。没有验证的扩展方案按设计说明，明确尚未测量的部分。

## 9. 简历模板与交付清单

实施后按真实范围填写：

> 设计并实现多业务线 RAG 知识服务平台，支持 [已完成领域] 的资料治理、混合检索、重排和引用问答；构建 [N] 道人工核对评估题，在固定测试集上将 [指标] 从 [A] 改善至 [B]，记录 [延迟/成本变化]；实现 [已验证的权限/版本/稳定性能力]，完成 [实际环境] 的部署及 [具体演练]。

不填尚未实现的模块。相对提升与百分点区分描述，容量目标和压测结果说明条件。没有实际用户和生产观察窗口时，不填写上线日活、商业收益或生产可用性成绩。

交付清单：README、架构与决策说明、资料来源与规模、评估题集与脚本、原始实验报告、失败案例、权限与一致性测试、部署说明、监控与故障演练、恢复与回滚记录、演示录像、项目讲解稿和简历描述。
