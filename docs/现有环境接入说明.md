配置来源为 `prompt/.env`。用户已确认：MongoDB、Milvus、Neo4j、MinIO 在 CPU 服务器上；BGE-M3、Reranker 在 GPU 服务器上。CPU 主机通过 SSH 本地转发访问 GPU 服务。文件末尾的 CPU/GPU 连接注释作为连接资料读取，不执行其中的内容；密码不写入本文或脚本。

## 当前配置与转换

已生成独立的本地 `.env.existing`，保留 `prompt/.env` 和原新环境 `.env.cpu`。转换只复制配置，不连接、初始化或修改远程数据库；生成文件被 Git/Docker 忽略，脚本拒绝覆盖。

| 原配置 | 项目配置 | 当前含义 |
|---|---|---|
| `MONGO_URL` / `MONGO_DB_NAME` | `MONGODB_URI` / `MONGODB_DATABASE` | CPU 环回地址上的 MongoDB，使用所提供的业务库名 |
| `NEO4J_USERNAME` / `NEO4J_PASSWORD` | `NEO4J_USER` / `NEO4J_PASSWORD` | 复用已有 Neo4j 身份 |

| `TEXT_LLM_*` / `VLLM_ENABLE=1` | `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` / `LLM_PROVIDER` | 当前为 GPU 上的 OpenAI 兼容接口与 qwen3-8b，不再强制 qwen-flash |

这里的 `127.0.0.1` 指 **CPU 主机**。本地 IDE 中没有建立 CPU 连接时，不能把它当作 Windows 本机服务地址。

`MINERU_MODEL_SOURCE=modelscope` 是本地模型来源说明，不能映射到 MinerU API 的 `pipeline/vlm` 模式。旧 Web MCP 配置目前不参与 RAG 主链路。

转换/源码加载命令：

```powershell

backend/.venv/Scripts/python scripts/prepare_existing_env.py --source prompt/.env --output .env.existing
```

在 CPU Linux 主机运行源码时对应 `export KB_ENV_FILE=.env.existing`。

## CPU 主机上的 SSH 隧道

原命令只转发 6006。根据确认的服务分布，还需转发 6008 与 6009；在 **CPU 服务器** 上运行：

```bash
ssh -CN \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:6006:127.0.0.1:6006 \
  -L 127.0.0.1:6008:127.0.0.1:6008 \
  -L 127.0.0.1:6009:127.0.0.1:6009 \
  root@connect.nmb1.seetacloud.com -p 39560
```

也可运行 `sh infra/scripts/gpu-tunnel.sh`。脚本额外要求已验证并保存 GPU SSH 主机密钥；可使用已有 SSH agent，或设置 `GPU_SSH_IDENTITY_FILE` 指向 CPU 主机上的私钥文件。交互密码登录可在 CPU 终端输入，不把密码嵌入命令或脚本。隧道进程需要持续运行，已有转发占用端口时不会悄悄改用其他端口。

右侧 `127.0.0.1` 指 GPU 主机的已发布端口；左侧指 CPU 的监听地址。仅 CPU 本机需要访问，因此上述监听绑定 CPU 环回地址。

## 容器如何访问 CPU 环回地址

新增 `infra/compose.existing.yml`，仅声明 `kb-import`、`kb-query`、`kb-worker`；不重建现有数据库或 GPU 模型容器。

该配置面向 Linux CPU 主机，使用 `network_mode: host`，使业务容器的环回地址与 CPU 主机一致。API 默认也绑定 CPU 环回地址，通过 SSH 隧道访问页面。若后续改成 bridge 网络，需要另行调整隧道监听与服务地址，不能直接沿用容器内 `127.0.0.1`。

```bash
# 配置校验，不会启动或迁移数据库。
docker compose --env-file .env.existing -f infra/compose.existing.yml config --quiet

# 确认以下兼容性条件后再启动业务容器。
docker compose --env-file .env.existing -f infra/compose.existing.yml up -d --build
```

## 仍需从实际服务核对的条件

配置文件提供了已有服务位置和部分凭据，不能据此认定全部协议已经兼容。下一次连接服务器时先检查：

1. GPU 嵌入 `/embeddings` 的请求/响应 Schema：必须提供真实 1024 维稠密与学习型稀疏结果，以及实际模型快照。当前代码已支持完整 endpoint，不会再次拼接路径；没有猜测现有服务的 JSON 字段或伪造 revision。
2. 重排的实际模型与快照、请求 Schema、候选 ID 的对应关系。已有服务不返回候选 ID 时，需要依据实际响应增加适配，不能直接把顺序当作身份。
3. MongoDB 是否为副本集、是否有认证，以及现有业务库集合是否与新工程 Schema 兼容。没有 `replicaSet` URI 参数不等于一定没有副本集，需读取实际拓扑；不支持事务时不能跳过事务保护。
4. 文件未声明 Milvus/Neo4j URI，当前保留 CPU 环回 `19530/7687` 的默认候选地址；确认实际发布端口、鉴权、Milvus 版本/Schema/collection 与已有数据后再写入配置。
5. MinerU 传输域名白名单仍需根据当前账户返回的准确域名补齐，空白会阻止文件传输。

未执行远程部署、真实推理或付费解析。复用环境不要执行新环境的 `init-infra`；`migrate` 会创建/修改校验器、索引与派生结构，先核对现有数据和隔离范围。当前应先做只读容器/接口/数据库拓扑检查，再决定需要的兼容调整。
